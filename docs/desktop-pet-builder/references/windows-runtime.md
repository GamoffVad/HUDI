# Проигрыватель и выпуск Windows-питомца

## Данные вместо конкретного персонажа

Храни имена действий, последовательности, fps/длительности, нейтральные позы, опору, диапазоны удержания, вероятности, cooldown и правила прерывания в manifest/спецификации. Не привязывай движок к `hood`, `pockets`, конкретным размерам спрайта или количеству глаз. Для нового персонажа проверь совместимость его действий и анатомии.

Существующий проект дорабатывай в его стеке. Для отдельного Windows-приложения с PNG-последовательностями подходит C# WPF: прозрачное окно без рамки, управление размером/положением, меню, ресурсы в архиве и ограниченный кэш декодированных кадров. Выбирай установленный совместимый .NET SDK; не фиксируй номер SDK из прошлого проекта. Для скелетного персонажа используй возможности его движка.

## Машина состояний

Если пользователь просит несколько питомцев в одном приложении, отдели библиотеку кадров, контроллер поведения и визуальный проигрыватель от встроенного персонажа. Дай настройки с выбором, предпросмотром и импортом пакета; сохраняй выбор отдельно от exe. Доступные действия определяй по manifest, а диапазоны удержаний — по данным пакета: нельзя использовать номера кадров одного героя для другого. При отсутствии роли пропускай соответствующую реакцию. Смена сохраняет размер, положение и подключение модели; во время незавершённого запроса согласуй смену с состоянием чата. Сохраняй незаписанные поля настроек при переходе к выбору персонажа.

Для ZIP-пакетов проверяй manifest, число и общий размер записей, размеры PNG до декодирования, все ссылки и длительности, границы удержаний и сами изображения. Не распаковывай недоверенные пути в произвольные каталоги и не запускай содержимое архива. Сначала проверь пакет во временном месте, затем добавь в коллекцию; повреждённый импорт не должен менять текущего питомца. Ограничивай кэш по памяти, проверяй повторный импорт, сохранение выбора, реальное переключение проигрывателя и возврат к встроенному персонажу.

Полезная структура: `rest → entry → action → optional hold → exit → optional transition → rest/next action`.

- Продвигай время по реальным длительностям кадров, а не числу вызовов отрисовки. Различай fps источника и частоту окна.
- Для автоматических действий используй очередь/перемешанный набор и интервалы покоя. Не повторяй постоянно один и тот же жест.
- Удержание обязано завершаться и иметь корректный выход. Проверь и короткий, и длинный вариант с воспроизводимым seed.
- Обычные события можно поставить в очередь до окончания жеста. Прерывания оставь для действий, которым пользователь назначил такой приоритет.
- Дыхание должно соответствовать персонажу и масштабу: сильное масштабирование всего силуэта выглядит как растягивание. Для жёсткого предмета или иного существа оно может быть неуместно.
- Не сбрасывай позу на каждом отсутствии события и не меняй оттенок при наведении через стили подсветки/opacity.

При растровом сглаживании рисуй целый кадр. Для проверки режима без дополнительных эффектов сравнивай native-size результат рендера с декодированным источником; допустимое округление зависит от формата premultiplied alpha. Это обнаруживает незапланированную перерисовку лица или цвета.

## Окно и взаимодействия

Проверяй прозрачность на настоящем рабочем столе. Hit test выполняй по видимой части текущего персонажа; прозрачные поля и мягкая тень не должны перекрывать клики без необходимости. Различай короткий клик и перетаскивание порогом движения.

Сохраняй размер, позицию, темп, паузу и режим поверх окон. Учитывай DPI, несколько мониторов и координаты виртуального экрана. Ограничивай окно доступной областью после смены мониторов. Используй уникальные для питомца mutex и каталог настроек, чтобы новый персонаж не конфликтовал со старым.

Наведение, курсорный взгляд, автозапуск и реакции на события Windows добавляй по запросу. Для событий запуска приложений/буфера обмена/файлов сначала проверь реальные доступные сигналы. Где достаточно типа события, не читай и не сохраняй содержимое документов или буфера обмена. Добавь подавление повторов и cooldown, иначе переключение окон запускает лавину жестов. Не обещай точное «файл скопирован» по любому изменению буфера обмена.

Ограничивай кэш по объёму памяти или размеру кадров. Не держи тысячи полноразмерных PNG в RAM. Сохраняй тень и полупрозрачные эффекты при уменьшении. Проверь использование CPU/RAM и частоту кадров на фактическом размере, включая длительный покой.

## Проверка перед заменой приложения

Проверки должны покрывать изменённое поведение:

1. Все кадры существуют; действия доходят до выхода; длинные удержания завершаются; автоматическая очередь выполняет ожидаемые действия.
2. Финальный кадр сохраняется в покое; первый кадр следующего перехода не скачет; включение/выключение дыхания не создаёт видимого смещения.
3. Прерывание и очередь соответствуют спецификации; при наведении нет незапрошенного сброса или смены цвета.
4. В просмотре фактического рендера нет двойных лиц, обрезанного силуэта, зелёных краёв, белых просветов или утраты тени.
5. Реальное окно запускается, проигрывает движения, реагирует на нужные действия и сохраняет настройки. Проверка одной машины состояний не заменяет проверку GUI.

Для обновления собери отдельную версию и сохрани предыдущую. Перед остановкой работающего процесса проверь его путь/идентичность. Не останавливай все `dotnet`, `python` или все похожие имена процессов. Перезапускай только авторизованный экземпляр и проверь, что запущена новая сборка. Установка этого навыка сама по себе не должна менять существующих питомцев.

При создании portable-сборки включи ресурсы, нужный runtime или явные зависимости и инструкцию запуска. Не сохраняй в ней секреты, чужие пути, данные аккаунта или логи с содержимым пользовательских документов. Записывай результаты QA и использованные генерации в проекте, а не в каталоге навыка.
